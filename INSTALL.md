# Hermes Agent — Docker Install

A clonable branch with macOS-compatible Docker compose, MCP-over-HTTP transport, and a tiny orchestrator script. Designed so the patches you'd otherwise have to apply by hand are already in the branch as real files — clone it and you have a working stack.

## Quick start

```bash
# 1. Clone this branch (gets the patched files + the install script + the SDK)
git clone --branch feat/hermes-install --single-branch --depth 1 \
    https://github.com/katysei/hermes-agent.git
cd hermes-agent

# 2. Run the orchestrator (generates API_SERVER_KEY, ensures ~/.hermes/, builds, starts)
./install-docker.sh

# 3. Add your model provider key (see below)

# 4. Use it
open http://localhost:9119                # dashboard
KEY=$(grep ^API_SERVER_KEY= .env | cut -d= -f2)
curl http://localhost:8642/v1/chat/completions \
    -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
    -d '{"model":"hermes-agent","messages":[{"role":"user","content":"hi"}]}'
```

Alternative (one-liner, no manual clone): `./install-docker.sh` from anywhere — if it doesn't find a Hermes checkout in CWD, it clones this branch automatically.

## What this branch carries

```
INSTALL.md                       — this file
install-docker.sh                — ~150-line orchestrator (no patching logic)
hermes_sdk.py                    — Python SDK (5 transports against the gateway)
docker-compose.yml               — patched: bridge networking + 127.0.0.1 ports + API on
docker/entrypoint.sh             — patched: optional MCP-over-HTTP side-process
docker/mcp_http_server.py        — new: streamable-HTTP transport for MCP
```

The three "patched" files live at their upstream paths, so cloning this branch IS the patched install. The orchestrator script just generates the API key, ensures the bind-mount dir exists, builds the image, and starts the containers — no file rewriting at install time.

The script does **not** create your provider API keys — you supply those.

## Two `.env` files — what goes where

Hermes uses two `.env` files in different locations. They do different jobs.

### `<install-dir>/.env` — compose runtime config

Lives next to `docker-compose.yml`. Auto-loaded by `docker compose` for `${VAR}` substitution. **Auto-generated by the install script.**

| Variable | Required? | Set by | What it does |
|---|---|---|---|
| `API_SERVER_KEY` | yes | install script | Bearer token for the OpenAI-compatible HTTP API on `:8642`. Without it the API server refuses to start. |
| `HERMES_UID` | recommended | `id -u` at invocation | Maps container's internal user to your host UID so files written to the bind mount stay owned by you, not phantom UID 10000. |
| `HERMES_GID` | recommended | `id -g` at invocation | Same idea for group. |

The script generates `API_SERVER_KEY` once with `openssl rand -hex 32`. You shouldn't need to touch this file unless rotating the key.

### `~/.hermes/.env` — runtime provider keys

Lives inside the bind-mount target (`~/.hermes/` on the host, `/opt/data/` inside the container). Read by Hermes itself for provider credentials. **You must populate at least one provider key.**

#### Required: at least one model provider

Pick whichever provider matches your `~/.hermes/config.yaml` (default upstream is `provider: anthropic`):

| Variable | Provider | Get from |
|---|---|---|
| `ANTHROPIC_API_KEY` | Anthropic (Claude / Opus / Sonnet / Haiku) | https://console.anthropic.com/keys |
| `OPENAI_API_KEY` | OpenAI (GPT-5 / GPT-4o / …) | https://platform.openai.com/api-keys |
| `OPENROUTER_API_KEY` | OpenRouter (unified router across models) | https://openrouter.ai/keys |
| `GEMINI_API_KEY` | Google Gemini | https://aistudio.google.com/apikey |
| `GROQ_API_KEY` | Groq | https://console.groq.com/keys |
| `DEEPSEEK_API_KEY` | DeepSeek | https://platform.deepseek.com/api_keys |
| `XAI_API_KEY` | xAI (Grok) | https://console.x.ai/ |
| `MISTRAL_API_KEY` | Mistral | https://console.mistral.ai/api-keys |

Example minimal `~/.hermes/.env`:

```dotenv
ANTHROPIC_API_KEY=sk-ant-api03-...
```

The corresponding `~/.hermes/config.yaml` top section would then be:

```yaml
model:
  default: claude-opus-4-7      # or claude-sonnet-4-6, etc.
  provider: anthropic
```

#### Optional: messaging bridges

Only set these if you want Hermes to bridge into messaging platforms.

| Variable | Platform | Notes |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | Telegram | Get one via @BotFather |
| `TELEGRAM_ALLOWED_USERS` | | CSV of user IDs allowed to message the bot |
| `DISCORD_BOT_TOKEN` | Discord | https://discord.com/developers/applications |
| `DISCORD_ALLOWED_USERS` | | CSV of user IDs |
| `SLACK_BOT_TOKEN` | Slack | `xoxb-...` from your Slack app |
| `SLACK_APP_TOKEN` | | `xapp-...` (for socket-mode) |
| `WHATSAPP_MODE` | WhatsApp | `web` or `business-api` |
| `WHATSAPP_ENABLED` | | `true` / `false` |
| `WHATSAPP_ALLOWED_USERS` | | CSV of phone numbers (`+15551234567,...`) |
| `EMAIL_IMAP_HOST` / `EMAIL_SMTP_HOST` | Email | Server hostnames |
| `EMAIL_ADDRESS` / `EMAIL_PASSWORD` | | Account credentials |
| `EMAIL_ALLOWED_USERS` | | CSV of sender addresses |

#### Optional: messaging-platform allow-lists (security)

Every bridge respects an `ALLOWED_USERS` CSV. If unset, the bridge accepts messages from anyone — bad for public bots. Set these the moment you enable a bridge.

## Optional env — `docker-compose.yml` (compose-level)

You can override these via the compose-level `.env` file too. They control the daemon itself.

| Variable | Default | What it does |
|---|---|---|
| `API_SERVER_HOST` | `0.0.0.0` (set by patch) | Host the HTTP API binds to inside the container. Don't change — `ports:` rule clamps external reach to `127.0.0.1`. |
| `HERMES_MCP_HTTP_PORT` | unset (MCP-HTTP off) | If set (e.g. `8000`), starts the MCP server over streamable HTTP as a side-process. Useful for the SDK's `via_mcp()` transport. |
| `HERMES_MCP_HTTP_HOST` | `0.0.0.0` | Where the MCP server binds inside the container. |
| `HERMES_MCP_HTTP_PATH` | `/mcp` | URL path the MCP server serves at. |
| `HERMES_DASHBOARD` | unset | Set to `1` to make the gateway container also run the dashboard (we use a separate `dashboard` service instead). |

To enable the MCP-over-HTTP transport, add to the compose `.env`:

```dotenv
HERMES_MCP_HTTP_PORT=8000
```

…and add `"127.0.0.1:8000:8000"` to the `ports:` of the gateway service in `docker-compose.yml`. After that, `Hermes.via_mcp("http://localhost:8000/mcp")` from Python works.

## Putting it together — minimal working setup

1. Run `./install-docker.sh` (creates `<install-dir>/.env` with `API_SERVER_KEY`, ensures `~/.hermes/` exists, builds + starts containers)
2. Add at least one provider key:
   ```bash
   echo "ANTHROPIC_API_KEY=sk-ant-..." >> ~/.hermes/.env
   ```
3. Verify:
   ```bash
   curl http://localhost:9119/                                  # dashboard: 200
   KEY=$(grep ^API_SERVER_KEY= <install-dir>/.env | cut -d= -f2)
   curl http://localhost:8642/v1/health -H "Authorization: Bearer $KEY"   # API: 200
   ```
4. Talk to it:
   ```bash
   docker exec -it -e HERMES_HOME=/opt/data hermes \
       /opt/hermes/.venv/bin/hermes chat
   ```

## Lifecycle

```bash
# State
docker compose ps
docker compose logs -f gateway

# Stop without deleting
docker compose stop

# Stop and remove containers (image and bind mount survive)
docker compose down

# Restart
HERMES_UID=$(id -u) HERMES_GID=$(id -g) docker compose up -d

# Full reset (keeps your ~/.hermes state)
docker compose down --rmi local
./install-docker.sh    # rebuilds everything
```

Your `~/.hermes/` is **never** deleted by any of these — it lives outside the container and outside the image. Sessions, memories, configs, and the kanban DB all survive `docker compose down --rmi all`.

## What's NOT auto-configured

The install script handles the Docker plumbing but explicitly **doesn't** generate or modify:

- Your provider API keys (`ANTHROPIC_API_KEY`, etc.) — add yourself
- Your `~/.hermes/config.yaml` model selection — defaults to whatever upstream ships (usually `claude-opus-4-7`); change to taste
- Your `SOUL.md` persona — optional; if you want a custom system prompt persona, write one at `~/.hermes/SOUL.md`
- Messaging bridge credentials — opt-in per bridge as documented above

## See the patches

The patched files are committed as real files in this branch, so you can diff them against upstream directly:

```bash
git diff main -- docker-compose.yml
git diff main -- docker/entrypoint.sh
# docker/mcp_http_server.py is a new file:
git show feat/hermes-install:docker/mcp_http_server.py
```

To revert any of them, just `git checkout main -- <file>`. No sentinel markers needed — the branch's commit history is the audit trail.
